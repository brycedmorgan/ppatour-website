# Outstanding Data Asks

> **API access model — read this first.** Our partner token authenticates as
> **`platformID=9`**, and access is a **per-path allowlist**. A path we aren't
> granted returns `403 {"Message":"Access denied for this platform.","Error":
> "platform access denied: platformID=9 path=..."}` — and **a deliberately
> nonsense path returns the identical 403**. So a 403 tells you *nothing* about
> whether an endpoint or its data exists; it only means we aren't allowlisted.
> Never conclude "the API doesn't have it" from a 403.
>
> Paths verified allowed for us (2026-07-29):
> `/v2/data/partner_rankings` · `/v2/data/ppa_tournaments` ·
> `/v1/data/users/{slug}` · `/v2/data/users/{uuid}/player_medals` ·
> `/v1/ppa/tournaments/{uuid}/tournament_events[/{eventId}]` ·
> `POST /v1/pb_data/json?sp_name=…` (stored-procedure gateway, its own
> allowlist: **only** `API_v2_Tourney_GetDetails` and `API_v2_Tourney_GetEvents`
> — every other SP name returns `400 "store procedure … is not allowed"`).

### Verification notes (no API ask was needed)

**Question was:** can last year's winners per stop/division be pulled from the
results API? **Yes — verified end-to-end 2026-07-29. No new API access needed.**

`POST /v1/pb_data/json?sp_name=API_v2_Tourney_GetEvents` with
`{"EventID":"<tournament_uuid>"}` returns **one row per division** (96 rows for
2025 Atlanta: 10 Pro + 67 Amateur + Junior) carrying the podium **directly** —
no bracket walking:

| Field | Use |
|---|---|
| `GoldTeamName` / `SilverTeamName` / `BronzeTeamName` | The podium, pre-joined ("JW Johnson & CJ Klinger") |
| `GoldTeamID` / `SilverTeamID` / `BronzeTeamID` | Team UUIDs if we need player-level links |
| `BracketLevelTitle` | `Pro` / `Amateur` / `Junior` — filter to `Pro` |
| `NoMedalWasAwarded` | **Must filter `=== false`** — qualifier rows are medal-less duplicates |
| `Title` | Division name, e.g. `"Mens Doubles Pro Main Draw"` |
| `PlayerGroupTitle` + `FormatTitle` | Structured division: `Mens`/`Womens`/`Mixed` × `Singles`/`Doubles` |
| `TotalRegistrations` | Per-division entry count (see ask 1 — may make it moot) |

Verified 2025 Atlanta Pro podium: Men's Doubles JW Johnson & CJ Klinger · Men's
Singles Ben Johns · Mixed Anna Leigh Waters & Ben Johns · Women's Doubles Anna
Bright & Anna Leigh Waters · Women's Singles Anna Leigh Waters. 91 of 96
divisions had a gold recorded, so amateur/junior champions are available too.

The equivalent is also derivable from the bracket feed
(`tournament_events/{eventId}` → the `inBracketType: "GS"` match carries both
finalists, names, seeds, scores and `winner`; `"B"` is the bronze match), but the
SP is one call per tournament instead of one per division.

**The remaining work is ours, not the API's: matching each 2026 stop to its 2025
counterpart.** Titles drift as sponsors change (`Veolia Cape Coral Open` →
`Zimmer Biomet Cape Coral Open`; `Open at the Las Vegas Strip` → `Rate Las Vegas
Open`), so title matching hit only 3/17. `venue_city` + `venue_state` gets ~11/17
but has real ambiguity — 2026 runs **two Mesa AZ stops** (Mesa Cup + Arizona
Open) and 2025 ran **two Las Vegas stops**, and Greater Zion moved city (St
George → Santa Clara UT) while keeping the venue. Genuinely new stops (Lakeville,
Newport Beach, Northbrook, Malibu) correctly have no prior year.
**Recommendation: a hand-authored `{2026 slug → 2025 tournament_uuid}` map** —
17 entries, unambiguous, and the honest "confirmed once last season's champions
are set" fallback already covers anything unmapped.

**(b) Ranking points earned per player per event — NOT AVAILABLE. This is the ask.**

Nothing we're allowlisted for exposes the points allocation behind a result.
`partner_rankings` gives only the *cumulative* total plus
`total_events_played{,_singles,_doubles,_mixed}`.

**✅ The discipline→WPR weighting IS exact — a partial unblock.** Verified
2026-07-29 across every ranked pro:

```
WPR = 0.5 × gender-doubles (dt 4 W / 5 M)
    + 0.35 × mixed          (dt 3, gender-split)
    + 0.15 × singles        (dt 1 W / 2 M)
```

reproduces the official combined points **exactly for all 1,296 men and all 737
women — 2,033/2,033, zero discrepancies.** Ben Johns:
`0.5·21800 + 0.35·23300 + 0.15·1600 = 19295` ✓.

So the **discipline-level** "where are their points coming from" breakdown is
buildable **today with no new access** — each pro's WPR splits cleanly into its
three weighted components, and the numbers will tie out to the published board.
That covers a large part of the ranking-wheel ask.

> ⚠️ An earlier revision of this doc claimed the weighting reproduced only
> 224/1,296. That was wrong — it used the **swapped** `division_type` mapping
> that `lib/division-rankings.ts` carried until 2026-07-29 (3 read as doubles,
> 4/5 as mixed). Correct mapping is in that file's header. Same root cause
> mislabeled discipline ranks on every athlete page; fixed in the same change.

**What is still genuinely missing is the per-EVENT grain** — which tournament
contributed which points. The weighting explains the *composite from discipline

### Bonus capability: `rank=<date>` returns real historical snapshots

Verified 2026-07-29 — the `rank` param is a genuine as-of date, not just a cache
key. The men's board reads Ben Johns `17,485` on 2026-04-26, `18,785` on 04-29,
`19,295` on 05-07, and row counts grow `1,103 → 1,149 → 1,150` as players become
ranked. **This unlocks rank/points-history charts with no new access**, on any
board including the per-discipline ones.

**It does NOT reliably yield per-event points.** Three reasons diffing two
snapshots around a tournament misattributes:

1. **Overlapping events.** The Atlanta 2026 window (Apr 27–May 3) also contains
   PPA Tour Australia PPA250, a Black Desert Challenger, and PPA Finals
   (from May 4) — four events in one diff.
2. **Publication lag.** Points post in discrete weekly-ish steps that do **not**
   align with event end dates: Ben Johns' `+1,300` had already landed by Apr 29,
   *before* Atlanta's gold-medal matches finished on May 3. So a window drawn
   around the event dates captures the wrong tournament's points. (Exact cadence
   unconfirmed — worth asking the API team.)
3. **52-week drop-off.** Expiring points net against gains, which bites hardest
   at annual anniversaries — precisely when a recurring stop is being viewed.

So: use snapshots for **history/trend**, never as a per-event points figure on
event pages. A derived number that looks authoritative and is wrong is worse than
the honest placeholder — same reasoning as the WPR-weighting note above.

### THE ASK: one allowlist grant. The endpoint already exists.

**We found the exact endpoint pickleball.com itself uses** (Wesley traced it
through the Next.js app, 2026-07-29). The rank-history view on
`pickleball.com/rankings/players/{slug}?type=rank-history` is rendered server-side
(RSC — no browser-visible JSON), and its server action `getPlayersRankingsHistory`
calls:

```
GET {API_URL_V2}/users/{playerUuid}/ppa_player_details
    ?divisionType={1..5}      # 1 W singles · 2 M singles · 3 mixed · 4 W doubles · 5 M doubles
    &bracketLevelId=2         # pro
    &topN=15                  # they use BEST_TOURNAMENTS_COUNT=14, +1 to detect "more exist"
    &startDate={unix}         # rolling 12-month window
    &use_camel_case=true
    &exclude_top=true         # optional — the "other tournaments" view
```

⚠️ Note the prefix: **`/v2/users/…`, not `/v2/data/users/…`** — a different path
family from everything else we call, which is why earlier probing missed it.

### Response shape (from `pickleballinc/pickleball`, `modules/rankings/ppr/types.ts`)

Per player, nested — **not** a flat per-event feed:

```
tournamentSummaries[]           // one per tournament
  ├─ cumulatedPoints            // player's total for that tournament
  └─ events[]                   // TournamentEventDetails — one per division
       ├─ eventUuid, eventTitle
       ├─ points                // ← ranking points earned at that division
       ├─ place, placeCarrier, notInTopFour
       ├─ gold/silver/bronze/fourth medalists
       └─ matches[]             // round, scores, opponents
```

The admin surface (`apps/manage/.../wp-rankings`, staff-only) shows the same data
flattened with **`ignoreInFinalCalculation`** — that is the "does this result
currently count" flag the ranking wheel needs. Confirm it's present (or derivable
from `notInTopFour` + `topN`/`exclude_top`) in the partner response.

**There is no "all players' points for event X" endpoint.** Event-page tables must
be built by aggregating per-player responses and grouping on `eventUuid`.

### Recommended architecture: one nightly sweep, all views derived

Fan-out sized against Atlanta 2026 (verified 2026-07-29): **393 distinct pro
players across 10 pro events / 590 matches, = 834 player×division entries.** Doing
that per event page is wasteful and will draw 429s.

Instead sweep the **ranked universe once nightly** (top N per discipline via
`partner_rankings`, ~450 calls), cache by player, then derive *every* view from
that one dataset — event-page points tables (group by `eventUuid`), athlete-page
breakdowns, and the ranking wheel. Participants per event are already free from
the bracket feed if a roster is needed.

**Two join details to verify first (they decide the whole adapter):**

1. **Does `events[].eventUuid` equal the `eventId` from
   `/v1/ppa/tournaments/{uuid}/tournament_events`?** Both are division-level
   UUIDs (Atlanta men's doubles main draw = `926f9336-be76-472a-bf0f-496d2c16054b`).
   If yes, the join is exact; if `eventUuid` is the *tournament*, match on
   tournament uuid + `divisionType` instead.
2. **Qualifiers are separate events** with their own `eventId` (Atlanta mixed:
   qual 56 matches, main 94). If points post against both, an event page must sum
   main + qualifier per player or the totals will read low.

Also confirm whether one call returns all disciplines or one call per
`divisionType` is required — that is the difference between ~400 and ~830 calls
per event's worth of players.
